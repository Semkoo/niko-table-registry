Loads rows from your API as the user scrolls (no pagination: the virtualized body prefetches the next chunk before the bottom). Users edit rows in the grid, and edits go back as a `created` / `updated` / `deleted` change set. The server checks each row. Failed rows stay dirty and highlighted so the user can fix and retry. The grid works with any backend, because it only calls two serializable functions you write.

## Live demo (mocked)

The demo runs against a **mock server**: an in-memory "database" of 400 employees with simulated delay that keeps your saves. Scrolling, editing, and saving all work out of the box. Everything in its `MOCK SERVER` section stands in for your backend.

## The wire contract

The grid never touches a database. It calls two functions with plain JSON shapes. Implement them with SQL, Prisma, Drizzle, Supabase, or any REST or GraphQL API:

```tsx showLineNumbers
type EmployeeQuery = { offset: number; limit: number } // LIMIT / OFFSET
type EmployeeQueryResult = { data: Employee[]; total: number }

// straight from useGridChanges().getChangeSet()
type EmployeeChangeSet = {
  created: Employee[] // INSERT
  updated: Employee[] // UPDATE ... WHERE id
  deleted: string[] // DELETE ... WHERE id
}
type EmployeeSaveResult = {
  succeededIds: string[]
  failedIds: string[] // rows the server rejected — stay dirty in the grid
}

declare function fetchEmployees(q: EmployeeQuery): Promise<EmployeeQueryResult>
declare function saveEmployees(c: EmployeeChangeSet): Promise<EmployeeSaveResult>
```

## Streaming rows on scroll

`DataTableVirtualizedBody` has `onNearEnd`. It fires once when the user renders into the last `prefetchThreshold` rows, so the next chunk loads _before_ they hit the bottom. Unlike a raw scroll listener, it also catches scrollbar jumps and first renders that are too short:

```tsx showLineNumbers
const loadMore = async () => {
  if (isFetching || !hasMore) return
  setIsFetching(true)
  try {
    const result = await fetchEmployees({ offset: loaded.length, limit: CHUNK_SIZE })
    setLoaded(prev => [...prev, ...result.data])
    setTotal(result.total)
  } finally {
    setIsFetching(false)
  }
}

<DataTableVirtualizedBody
  estimateSize={37}
  fixedRowHeight
  prefetchThreshold={10}
  onNearEnd={() => {
    if (hasMore && !isFetching) void loadMore()
  }}
>
```

## Merging chunks without losing edits

New chunks arrive _while the user is editing_, so the sync can't just replace the grid's rows. Do this instead: reset change tracking to the server snapshot, then rebuild the rows. Keep every dirty row's current values (edited rows in place, locally created rows added at the end):

```tsx showLineNumbers
const serverRows = React.useMemo(() => loaded.map(toGridRow), [loaded])

React.useEffect(() => {
  if (lastSyncedRef.current === serverRows) return // once per snapshot
  lastSyncedRef.current = serverRows
  const dirtyIds = new Set(changes.dirtyRowIds)
  changes.reset(serverRows) // baseline = what the server has
  grid.updateRows(
    prev => {
      const prevById = new Map(prev.map(r => [r.id, r]))
      const serverIds = new Set(serverRows.map(r => r.id))
      const merged = serverRows.map(r =>
        dirtyIds.has(r.id) && prevById.has(r.id) ? prevById.get(r.id)! : r,
      )
      for (const r of prev)
        if (!serverIds.has(r.id) && dirtyIds.has(r.id)) merged.push(r)
      return merged
    },
    { history: false }, // data loads don't belong in the undo stack
  )
}, [serverRows, grid, changes])
```

Comparing against the new baseline marks the kept rows as dirty again automatically.

## Saving with reconcile

```tsx showLineNumbers
const onSave = async () => {
  const { created, updated, deleted } = changes.getChangeSet()
  const result = await saveEmployees({
    created: created.map(toEmployee),
    updated: updated.map(toEmployee),
    deleted,
  })
  // succeeded rows become clean; failed rows stay dirty (highlight them
  // via changes.failedRowIds in getRowClassName)
  changes.reconcile(result)
  // mirror the successful writes into the local server snapshot
  // (or refetch) — the sync effect re-baselines from it
  setLoaded(applySuccessfulWrites)
}
```

## Key points

- **Prefer `onNearEnd` over `onScrolledBottom`** for virtualized infinite scroll. It is driven by the virtualizer's row index, fires once per approach, and handles fast scrollbar drags.
- **Convert at the boundary.** API rows are plain JSON. Grid rows hold a `CellState` per column. Keep two small mappers (`toGridRow` / `toEmployee`) so the rest of the file never mixes the shapes.
- **The server owns validation.** The demo rejects rows without a name or a valid email. `reconcile` keeps them dirty, and `failedRowIds` drives the row highlight.
- **Raise `maxRows`.** `useDataGrid` caps rows at 200 by default. Set it above the number of rows you expect to load.
- **Created-row ids stay client-generated.** `useGridChanges` does not remap ids. Either store the client id or reload after save.
